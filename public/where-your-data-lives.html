How Databases Find a Needle in a Billion-Row Haystack

A database can find one record among a billion in milliseconds. The secret is the same idea behind a book's index — and a clever tree.

Builds on↩ The Two Hard Problems

Type a name into an app and it finds your record instantly — even if the database holds a billion rows. How? Not by reading all billion (that’d be the slow O(n) scan we met earlier). Databases use a structure so clever it feels like cheating: the index. It’s the difference between flipping through every page of a book and using the index at the back. Today: how databases stay fast at absurd scale.

The index: don't scan, look up

Without help, finding a row means checking every row — fine for 100, hopeless for a billion. An index is a separate, sorted structure that maps a value (say, a username) to the exact location of its row. Look up the value in the sorted index and jump straight there. It’s precisely the index at the back of a book: the book’s content is unsorted for this purpose, but the index is sorted so you can find ‘photosynthesis → page 214’ fast.

Why a B-tree, not a plain list

Databases usually build indexes as a B-tree — a wide, shallow, always-balanced tree. Each step down the tree eliminates a huge chunk of possibilities, so finding anything takes O(log n) steps: for a billion rows, roughly 30 steps instead of a billion. And because it stays balanced and its nodes map neatly onto disk blocks, it’s fast even when the data lives on slow storage. That’s the workhorse behind almost every database you’ve ever used.

⚠️
Indexes aren't free

Every index speeds up reads but slows down writes — because each insert or update must also update the index — and it costs storage. So you index the columns you search on, not everything. ‘Add an index’ is the first fix for a slow query, and ‘too many indexes’ is a common cause of slow writes. Databases are one long exercise in this read/write trade-off.

The gist

  • Scanning every row is O(n) — hopeless at scale; an index lets you jump straight to a row.

  • An index is a sorted side-structure mapping a value → its row’s location (like a book’s index).

  • Databases use B-trees: wide, balanced, ~O(log n) — a billion rows in ~30 steps.

  • B-trees stay fast even on slow disk because they map onto storage blocks.

  • Indexes speed reads but slow writes and cost space — index what you search on.
