Consistent Hashing: How Big Systems Add Servers Without Chaos

The quietly brilliant idea that lets Discord, DynamoDB, and every CDN grow one machine at a time.

Suppose you run 4 cache servers and decide which server holds a key with hash(key) % 4. It works perfectly — until you add a fifth server. Now it’s % 5, almost every key maps somewhere new, and your entire cache misses at once. That single stampede has taken down real systems. Consistent hashing is the trick that makes adding or losing a server move only a tiny slice of your data instead of all of it.

The problem with the obvious approach

The natural way to spread keys across N servers is server = hash(key) % N. It’s fast and evenly balanced. The catch is hidden in that N. The moment N changes — you add capacity, or a machine dies — the divisor changes, so the remainder changes for nearly every key.

Concretely: with 4 servers, roughly 75% of keys get a new home when you move to 5. For a cache that means a near-total miss and a thundering herd of requests hitting your database at once. For a sharded database it means moving three-quarters of your data across the network just to add one node. That’s not growth — that’s an outage with extra steps.

💡
The core idea

Instead of mapping keys to servers directly, map both keys and servers onto the same circle (the “hash ring”). A key belongs to the first server you meet walking clockwise from where the key lands. Now a server only owns the arc between it and its neighbor — so adding or removing one only disturbs that arc.

Why only a small slice moves

When you add Server D onto the ring, it drops into one specific spot and steals only the keys sitting between it and the previous server clockwise. Every other key still resolves to exactly the same server it did before.

The math is clean: with N servers, adding one moves on average 1/(N+1) of the keys, not 3/4 of them. Lose a server and its arc simply flows to the next node clockwise — again, only that node’s neighborhood is affected. This is the property the name promises: the mapping stays consistent as membership changes.

⚠️
The catch: uneven load

Placing each server at a single random point tends to create lopsided arcs — one machine ends up owning a huge slice while another sits nearly idle. Real systems fix this with virtual nodes: each physical server is hashed onto the ring in many places (say 100–500 tokens). More points means smoother, more even coverage — and when a server dies, its load spreads across many neighbors instead of dumping entirely onto one.

How a lookup actually works

  1. 1

    Hash the key to a point on the ring (e.g. a 32-bit or 128-bit hash of the key string).

  2. 2

    Walk clockwise from that point to the first server token you hit. In practice this is a binary search over a sorted list of token positions — O(log V) where V is the total number of virtual nodes.

  3. 3

    That token’s physical server owns the key. Read or write there.

  4. 4

    When membership changes, only recompute the handful of keys whose owning arc changed — everything else is untouched.

Where you've already used it

Consistent hashing isn’t academic — it’s load-bearing infrastructure. Amazon DynamoDB and Apache Cassandra partition data across nodes with it. Discord uses it to route millions of users to the right chat servers. Every CDN (Akamai, Cloudflare) uses it to decide which edge cache holds which asset. Memcached client libraries like ketama popularized it for exactly the cache-stampede problem we opened with.

It’s one of those ideas that looks small — “put things on a circle” — but quietly makes horizontal scaling safe.

The gist

  • hash(key) % N breaks catastrophically when N changes — nearly every key remaps at once.

  • Consistent hashing puts keys and servers on a ring; a key belongs to the next server clockwise.

  • Adding/removing a server moves only ~1/N of keys, not most of them.

  • Virtual nodes (many tokens per server) keep load even and spread failures across neighbors.

  • It’s the backbone of Cassandra, DynamoDB, Discord routing, and every CDN.
