The Numbers Every Programmer Should Know

Your CPU is blindingly fast — so why is software ever slow? Because not all memory is equal, and the gaps between them are staggering.

Builds on↩ What a computer really does

Yesterday we saw the CPU rip through instructions billions of times a second. So why does anything ever feel slow? Here’s the secret that separates people who write code from people who make it fast: the CPU spends most of its life waiting — for data to arrive from memory. And the difference in wait times between the fastest and slowest storage isn’t 2x or 10x. It’s roughly the difference between a second and a decade. Internalize these gaps and you’ll understand performance, caching, and half of systems design.

The memory hierarchy

There isn’t one kind of memory — there’s a hierarchy, trading speed for size and cost. Near the CPU sit tiny, blisteringly-fast stores; far away sit huge, slow ones:

  • CPU registers / L1 cache — tiny, essentially instant.
  • L2 / L3 cache — small, very fast.
  • RAM (main memory) — gigabytes, but ~100x slower than cache.
  • SSD — huge, but far slower than RAM.
  • Network / disk far away — enormous, and glacial by comparison.

The CPU can only compute on data that’s close. If the data it needs is far down the hierarchy, it stalls — doing nothing — until it arrives.

📊
The gaps, scaled to human time

Multiply every real latency by ~a billion so it’s human-readable. L1 cache = 1 second. RAM = a couple of minutes. An SSD read = a few days. A spinning disk seek = a few months. A network round-trip across the world = years. Same units, wildly different worlds. When your program is slow, it’s almost never ‘too much math’ — it’s waiting on the far end of this ladder.

Locality: the trick that saves us

The reason computers aren’t hopelessly slow is a pattern called locality of reference: programs tend to reuse the same data (temporal locality) and data stored near it (spatial locality). Hardware bets on this by caching — quietly keeping recently- and nearby-used data in the fast tiers.

So the practical lesson for building anything fast: keep the data you need close, and touch it in predictable patterns. Looping over a compact array is fast because it streams neatly into cache; chasing pointers all over memory is slow because every jump risks a trip down the hierarchy. This single idea — mind where your data lives — reappears in caching, databases, and distributed systems throughout this track.

The gist

  • The CPU is fast, so real-world slowness is usually waiting for data, not computing.

  • Memory is a hierarchy: registers/cache → RAM → SSD → network, trading speed for size.

  • The latency gaps are enormous — scaled up, L1 ≈ 1 second while a global network hop ≈ years.

  • Locality of reference (reusing recent/nearby data) lets caching hide most of the cost.

  • To go fast: keep needed data close and access it in predictable patterns (arrays beat pointer-chasing).

Q1

If a modern program feels slow, what’s the most common underlying cause?

CPUs are extremely fast at arithmetic; the usual bottleneck is stalling while data travels up from RAM, disk, or the network.

Q2

Roughly how does RAM latency compare to L1 cache latency?

RAM is on the order of 100x slower than L1 cache — scaled to human time, seconds vs. minutes. That’s why keeping hot data in cache matters so much.

Q3

What does ‘locality of reference’ let hardware do?

Programs reuse recent data (temporal) and nearby data (spatial), so caches keep that data close — hiding most of the latency ladder.
